## 5. 发现的问题与已实施修复

### P1-1：团队工作存在固定 500 条上限，长期会漏数

原实现把团队工作结果硬限制为 500 条，工作台统计、逾期补交和多门店下钻会在数据增长后静默漏数；接口虽然存在 `page/size` 参数，但控制器未明确绑定参数，服务也未真正分页。

已修复：

- 明确绑定 `status`、组织、营业日期、起止日期、`page`、`size`。
- 页大小限制为 1–200；负页码、非法大小和倒置日期返回 400。
- 使用稳定排序和 `limit/offset`，移除固定 500 条上限。
- Web 按 200 条分页拉取、去重并设置安全页数上限。
- 新增分页稳定性、边界和非法区间集成测试。

### P1-2：快速切换岗位/组织可能出现旧请求覆盖新页面

慢响应可能在用户已经切换任职后返回，把上一个岗位的数据写入当前工作台，属于权限展示和决策数据的严重可靠性问题。

已修复：

- 通用资源 Hook 增加请求代次保护。
- 任职、组织或请求参数变化后，旧请求即使后返回也不能更新状态。
- 组件卸载时使在途请求失效。
- 新增“旧响应晚到”和“卸载后不更新”回归测试。

### P1-3：规则/工作包仅靠菜单隐藏，后端写接口权限过宽

仅隐藏菜单不能阻止直接调用 API；CEO、集团副总、店长等非管理员理论上可能通过已有权限发布配置，与“仅管理员开放”的业务冻结要求不一致。

已修复：

- 新数据库迁移从所有非管理员标准角色移除规则、工作包配置模块及管理/发布/分配动作。
- 前端标准角色矩阵同步移除入口。
- 后端岗位权限发布增加强制白名单：只有 `PLATFORM_ADMIN` / `GROUP_ADMIN` 可把配置能力发布给岗位。
- 工作流所需只读权限保留，避免员工执行既有工作包时被误伤。
- 原本以 CEO 身份进行配置的测试全部改为专用平台管理员夹具，防止测试继续固化错误权限。

### P1-4：企微手机端附件预览依赖延迟弹窗，可能被拦截

移动端 WebView 对异步 `window.open` 限制严格，导致图片“查看”无反应或出现下载页。

已修复：

- 图片和 PDF 使用当前页面内预览，不再依赖异步新窗口。
- Word/Excel 等不适合浏览器直接显示的类型明确走下载。
- 对临时 Blob URL 做关闭回收，避免长时间使用时内存泄漏。
- 工作记录附件和任务附件统一使用同一预览行为。

### P1-5：部分岗位移动端存在无权限 KPI 入口

董事长、行政人事主管、行政人事的移动端五栏曾显示 KPI，但桌面模块和后端权限没有 KPI，点击后会成为死入口。

已修复：

- 董事长该栏改为“消息”。
- 行政人事主管、行政人事该栏改为“消息”；行政人事 KPI 管理员继续保留 KPI。
- 新增不变量测试：每个冻结岗位的每个移动端标签必须能解析到该岗位可用模块。

### P1-6：依赖和 CI 门禁不足，回归容易只在个人电脑上被发现

已修复：

- 明确 pnpm 版本和 Web 测试脚本。
- 新增 GitHub Actions：Core API、OTA、Web 三条独立任务。
- Web 使用冻结锁文件安装，随后运行回归、类型检查和生产构建。
- CI 最小权限为只读，并启用同分支并发取消，减少旧构建占用。

### P2-1：工作台逾期口径可能长期累积历史日清

已核对并修正当前工作范围：即时日清只统计当天，当前月只保留应继续追踪的非即时工作和当月逾期后补交；逾期判定使用首次提交时间，不因后续修改时间变化。

### P2-2：常用查询缺少针对工作台下钻的组合索引

新增工作实例范围/日期查询索引和组织闭包后代查询索引，降低多门店、按月和组织下钻时的数据库扫描成本。

### P2-3：前端主包偏大

把工作台、配置、企微、日报、日运营、KPI、投资等大页面按路由懒加载。主入口从约 583 kB 降至 355.04 kB，gzip 从约 170 kB 降至 106.20 kB。

### P2-4：通用构建产生未定义环境变量告警

`index.html` 中存在未使用的 `%VITE_AUTH_MODE%` HTML 占位符，而实际鉴权模式由 `import.meta.env.VITE_AUTH_MODE` 读取。已删除无效占位符，生产构建无该告警。

## 6. 规则与数据口径审查

1. **即时日清与长期任务分开**：日工作清单漏交不能永久累加到当前异常；历史事实保留在历史记录，当前异常只反映当日即时任务和仍未闭环的非即时任务。
2. **逾期后补交不抹掉逾期事实**：使用首次提交时间判断是否逾期；后续编辑不会把迟交改成按时完成。
3. **完成率分母必须固定**：当日完成率以截至当前应完成工作为分母；截至当日月完成率以月初至当天应完成工作为分母。未来日期不能提前进入分母。
4. **版本不可变**：已发布工作包和标准不原地修改；调整生成新版本。删除配置表示新版本不再包含，历史任务、评价和证据仍可审计。
5. **配置权与执行权分离**：管理员配置/发布，业务岗位执行、复核和评价。董事长的任务派发是业务动作，不等同于后台配置权。
6. **多任职数据范围取当前任职**：用户可有多岗位，但每个请求必须以当前业务任职和授权组织树计算范围，不能把账户拥有的所有岗位权限简单合并后越权。
7. **删除与审计分离**：员工永久删除后不应出现在活动企微绑定列表；历史操作通过脱敏标识和审计表保留，不能反向恢复为可登录员工。
8. **区域经理继续冻结**：目前不把“区域经理”模糊映射到 OTA 运营经理或集团副总，避免未定义的数据范围被自动放开。

## 7. 架构与稳定性评价

### 7.1 当前较稳健的设计

- PostgreSQL + Flyway 迁移可从空库连续构建到 V54，数据库变更可追踪。
- 关键写操作存在租户/组织范围、权限检查和状态约束，不完全依赖前端。
- 工作包和评价标准采用发布版本，适合审计和历史复盘。
- 工作实例、证据、复核、评价、整改任务之间有明确标识和状态流转。
- 企微绑定、员工任职与业务通知相互解耦，避免“绑定成功”自动开启群推送。
- OTA contracts/helper/API/worker 分模块，测试隔离程度良好。
- Web 通过权限码决定可见模块，再由角色策略做兼容收窄；未知自定义岗位不会被前端凭空授予功能。

### 7.2 需要继续治理的架构风险

以下不是本轮应在没有专项迁移方案时强行重写的问题，但已经构成后续迭代风险：

- `WorkPackageService` 约 2,041 行。
- `PositionManagementService` 约 1,977 行。
- `OrganizationService` 约 1,638 行。
- `WeComDirectoryOnboardingService` 约 1,605 行。
- `KpiAssessmentService` 约 1,518 行。
- `WeComDirectoryOnboardingAdministrationService` 约 1,511 行。
- `DailyReportService` 约 1,361 行。
- Web `App.tsx` 约 1,340 行，`resources.ts` 约 998 行。

这些“大服务/大入口”把查询、授权、状态流转、序列化和通知编排集中在同一文件，容易产生以下问题：

- 修改一个流程时误伤另一个流程。
- 事务边界和幂等边界难以一眼识别。
- 单元测试需要搭建过多依赖。
- 同一权限或状态规则在多个方法中逐渐漂移。

建议按业务边界渐进拆分，而不是一次性重构：

1. 工作包拆成配置发布、实例生成、员工提交、团队复核四个应用服务。
2. 组织拆成组织树、岗位模板、人员任职、有效身份四个边界。
3. 企微拆成邀请令牌、OAuth 身份、入职审核、绑定异常四个边界。
4. Web 将路由外壳、身份上下文、业务任职切换和弹窗编排从 `App.tsx` 分离。
5. 每次拆分保持 API 契约和数据库结构不变，先补契约测试再迁移实现。

发布脚本方面，仓库仍存在面向旧 `TECH-V0.2` / V13 门禁的历史脚本，而当前数据库已到 V54。该脚本不应被误用于当前 Pilot.8 发布。建议后续建立版本无关的当前发布流水线，并把旧脚本显式标记为历史只读。

## 8. 仍需真实环境 UAT / 运维证据

下面这些能力无法由本地模拟或隔离数据库替代，必须上传 UAT 证据：

| 项目 | 最低证据 |
| --- | --- |
| 企业微信应用入口 | iOS/Android 各一次，从工作台打开应用，OAuth 回调返回 HTML 而不是文件下载 |
| 企业微信邀请 | 同一二维码由至少 2 名员工在有效期内注册；过期后拒绝；总部和门店均可选择 |
| 真机拍照 | 调用相机、权限拒绝/允许、时间戳/门店/证据编号水印、多图和房号分组 |
| 文件链路 | 图片、PDF、Word、Excel 分别上传、持久化、预览/下载、权限拒绝、删除/补充 |
| 文件安全 | 生产病毒扫描或隔离服务实际运行；恶意样本演练使用安全测试样本并留日志 |
| 企微通知 | 任务提醒、逾期升级、审核结果、整改通知的真实卡片和跳转链接 |
| PMS/OTA | 使用真实凭据的只读同步、限流、超时、重试、部分失败和幂等验证 |
| 并发与容量 | 目标员工数、门店数、工作实例数下的峰值生成、提交、团队下钻压测 |
| 数据库恢复 | 生产同版本备份 → 新实例恢复 → Flyway 校验 → 核心抽样查询 → 回滚演练 |
| KPI 工作簿 | 使用批准版 KPI 文件导入，核对岗位、权重、舍入、缺勤/迟交等边界 |
| 线上 UAT | 从云域名完成一次“配置—执行—复核—评价—整改—验收—日报/KPI”全流程 |

建议 UAT 每条记录至少包含：环境、版本/Commit、岗位、组织/门店、前置数据、操作时间、预期、实际、截图/视频、请求追踪号、数据库审计号、验收人和结论。涉及员工手机号、UserID、证件和图片时必须脱敏。

## 9. 发布门禁建议

合并或部署前按以下顺序执行：

1. 审查当前差异，确认数据库 V54 的角色收紧符合业务签字。
2. 在 CI 中完成 Core API、OTA、Web 三条任务。
3. 在预发布环境执行 V54 并验证非管理员不能发布规则/工作包。
4. 对管理员、CEO、董事长、副总、店长、主管、员工、行政人事各抽一个真实账号做冒烟。
5. 完成第 8 节中的企微入口、文件链路和备份恢复关键证据。
6. 再生成发布制品、部署云端、验证健康检查和版本 Commit，最后推送/打标。

本轮修改当前仅位于 `codex-review` 工作区；在用户明确要求合并、推送或部署之前，不会自动改变主线或云端。
