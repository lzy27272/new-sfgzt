# 库存成本闭环：第三阶段——布草洗涤台账

## 交付边界

本地实现，接续规格与单位换算、日清耗用审核联动。入口为「门店库存与固定资产 → 布草洗涤台账」。本次不执行合并、GitHub 推送或云端部署。

本阶段提供真实业务台账与费用事实，不是已完成的月结、付款或 PMS 经营成本分析。

## 操作流程

1. 在门店物品配置中新建或导入布草，按基础单位登记真实期初库存。
2. 在洗涤台账中展开「布草单价与在洗数量」，为每种布草单独填写洗涤单价。它与采购参考成本完全不同；未配置不能送洗，明确设置 0 表示免费洗涤。
3. 登记供应商、实际送洗日期、布草及数量。默认只按基础单位填报，不把“包”误当成“条”；送洗单冻结名称、单位、单价及配置版本。
4. 分批验收：填写本次合格数量、不合格返洗数量、已核实报损数量。返洗或报损必须填写原因；报损还需单独勾选确认。
5. 原因清晰的更正通过「冲销本次回收」实现，再重新登记正确事实。有有效回收时不能直接取消送洗；全部冲销后才可取消。任何原始明细都不删除。

## 核算口径

| 事件 | 总库存 | 在洗数量 | 洗涤费用 |
| --- | --- | --- | --- |
| 送洗 | 不变 | 增加 | 不计费 |
| 合格回收 | 不变 | 减少合格数量 | 合格数量 × 冻结洗涤单价 |
| 不合格返洗 | 不变 | 仍在洗，不另外累加 | 不计费 |
| 确认损坏/丢失 | 减少，另记加权平均库存损失 | 减少报损数量 | 不计洗涤费 |
| 冲销回收 | 恢复该回收产生的报损原数量和原金额 | 恢复原合格/报损数量 | 原费用不再纳入有效费用 |
| 取消无有效回收的送洗单 | 不变 | 释放该单占用 | 不计费 |

- 同一回收明细的合格 + 返洗 + 报损，不得超过尚在洗数量。没有查明的短缺保持“尚在洗”，不能无原因直接核销。
- 可送洗 = 当前总库存 − 有效送洗单尚在洗数量。重复送洗和手工出库不得侵占在洗数量。
- 日清登记的布草使用量只是周转事实，不自动再生成送洗或洗涤费，避免同一事件重复核算。
- 数量、单价最多四位小数，服务端使用精确十进制计算；每条回收明细的费用四舍五入到四位小数，展示保留到四位。浏览器预估不是最终记账依据。
- 已停用布草不得新增送洗，但原送洗单仍可验收、冲销和追溯，防止停用后无法处理历史在洗。
- 有洗涤配置后，布草基础单位和分类不能改变；规格或品类变化应新建物品，避免历史数量语义改变。
- 供应商本阶段记录名称，不包含供应商主数据、合同价阶梯、税额、付款和对账结算功能。

## 权限与安全

- 查看：`store-resource.read` + 门店范围；配置单价：`store-resource.item-manage` + 门店范围；送洗、验收、报损、更正：`store-resource.movement-create` + 门店范围。
- 不因为能够查看库存而自动授予记账权，不修改任何岗位默认授权；由管理员按门店确定操作人员。
- 所有新表 FORCE RLS 并对读写应用租户策略；请求同时检查门店归属，不只依赖前端隐藏按钮。
- 创建送洗和回收使用请求幂等键；相同内容重试返回原单，不重复计费。更正使用原单版本并对相同原因幂等。前端同一请求网络失败重试保留编号，修改内容后生成新编号。
- 变动按「送洗单 → 有序物品行 → 库存余额」加锁；新增送洗按有序物品锁后创建新单。整单失败回滚费用、库存、审计，不能部分入账。
- 冲销后若在洗数量会大于总库存（例如已再次送洗或出库），整体拒绝，需先核对后续流水，不允许为更正制造负库存。

## 数据与升级

- V65：`store_laundry_rate`、`store_laundry_order`、`store_laundry_line`、`store_laundry_receipt`、`store_laundry_receipt_line`。回收明细及送洗明细不可覆盖；头表只允许受控状态流转。
- 库存流水新增 `LAUNDRY` 来源，关联回收单。正常洗涤不生成采购消耗；仅确认报损与其冲销生成库存流水。
- 升级只建结构及约束，旧库存数量、金额与工作记录不变，不回填推算历史洗涤费。
- 不开启自动清理新台账，结构化洗涤记录、费用、操作者与更正原因留存。图片五天清理不影响台账；本阶段无独立洗涤附件上传入口。
- 列表按送洗日期分页，每页25单，支持尚在洗、已全部核对、已取消过滤及完整单据历史。

## 测试与上线门槛

2026-09-18 本地结果：后端10个相关测试类共47项通过，前端210项通过，普通构建及Pilot构建通过，差异格式检查通过。真实浏览器及手机验收不包含在这些自动化结果中。

- 后端覆盖：分批回收、冻结价格、返洗不计费、库存占用、并发与重试、超收拒绝、报损双确认、原成本冲销、后续出库冲突、整单回滚、门店与权限隔离、历史不可变。
- 迁移覆盖：非超级用户、无 BYPASSRLS 的迁移账号升级；升级前后库存完全相同；新表读写租户隔离。
- 前端覆盖：精确费用预估、数量/版本/原因校验、真实 React 表单渲染、只读权限、错误/成功提示以及提交中锁定。
- 当前 Browser 插件缺少运行文件，未完成真实浏览器点击及企微手机端验收。发布前仍须在测试环境按本页操作流程走一遍真实页面，特别核查手机键盘、回收表单、明细滚动定位和提示可见性。
- 上线应使用同一主线版本打包后端和前端，备份数据库并验证 V63 → V64 → V65 连续升级，先授权一个测试门店验收再逐步开放。不能只上传 Web 包。

## 下一阶段

成本分析与月结：耗品、清洁用品实际耗用 + 合格回收洗涤费 + 布草报损损失分栏汇总，按门店/日期/分类/月度统计。冲销应按更正时点记入调整，不根据当前有效状态重算已经关闭的月份；需要月结快照、关账校验、授权重开和审计。之后接 PMS 实际间夜，计算单间夜耗品及洗涤成本。以上功能本次尚未开发。
