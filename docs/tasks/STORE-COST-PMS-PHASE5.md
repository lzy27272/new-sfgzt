# 库存成本闭环：第五阶段——PMS用房间次与成本

## 交付状态

本地开发，接续第四阶段。入口：门店库存与固定资产 → 成本分析与月结 → PMS用房间次与成本。

本阶段实现的是**PMS脱敏汇总读取、口径校验和成本分析页面**，不是新建一个向PMS厂商抓取数据的连接器。未登录PMS或调用厂商接口，未修改云端配置、合并、推送或部署。真实门店数据源尚需映射和口径验收，不能把测试数据通过理解为线上已经接通。2026-09-20用户明确同房当天使用两次计“2次”，现按全部用房间次统计；此决定替代9月19日的房晚当量、强制四项明细和钟点折算要求。

接口：`GET /api/v1/store-resources/hotels/{hotelId}/costs/per-room-use?periodType=MONTH&period=2026-08`。`DAY`使用`YYYY-MM-DD`；`MONTH`使用`YYYY-MM`。旧`per-room-night`路径仅保留弃用别名，返回新版本间次契约，不再返回旧房晚字段；前后端应一起发布，旧客户端会拒绝未知口径。只读权限沿用 `store-resource.read` 加门店范围；不提供通过请求参数指定PMS门店编号、文件路径或租户的功能。

## 计算与日期

- 每间次耗品成本 = 同期已入账耗品净成本 ÷ 已核对的PMS全部用房间次。
- 每间次清洁用品成本 = 同期已入账清洁用品净成本 ÷ 已核对的PMS全部用房间次。
- 每间次洗涤成本 = 同期合格回收洗涤净费用 ÷ 已核对的PMS全部用房间次。
- 全部用房包括过夜、免费、自用和钟点使用。按营业日实际使用间次计数，同房当天钟点一次、过夜一次计2间次；不按房号去重，不按钟点时长折算，不要求客人明细。
- 确认包含上述范围的总间次即可计算，不强制用户提供完整PMS日报或四类分项。可选的四类分项须互斥：免费/自用优先，其余收费使用区分过夜与钟点；同一次使用不重复归类，不等于将同房不同次使用合并。
- 月成本按当期总成本除以累计间次，不取每日单价的简单平均。例如两天成本20元、40元，用房2、8间次，月累计为60÷10=6元/间次，而不是(10+5)÷2=7.5元/间次。
- 采购、期初库存、布草周转次数、未验收洗涤、报损、盘点调整和固定资产原值不混入上述三项。
- 分子沿用V66成本账的**入账日期**，不改成原始业务日期或当前配置单价；历史补录、冲销可能造成当期负数，页面单独提示非原日期入账记录。
- 这是门店管理摊分，不是每间房的直接实际消耗，也不是全店经营总成本。可选分项只是使用量，不代表已核算出各类型各自实际耗用成本。
- 间次必须是非负整数，金额与比值使用精确十进制，每间次成本四位小数，同比环比两位小数。涨跌幅使用未截断的两个原始比值交叉计算，不拿显示后的四位小数继续算。
- 日模式默认最近已日结营业日：根据门店时区、日切时间及日结宽限期判断，支持超过一天的宽限期。当日尚未日结不生成比值。
- 月模式默认当月截至最近已日结营业日；历史完整月用完整月；当月还没有已日结日期时明确提示，不借用上月数据。
- 日环比为前一日、日同比为上一年对应日期；月环比为上月同期、月同比为去年同期。完整月与完整对比月比较；月中按相同日号截齐，短月/闰年到对应月末。页面展示双方实际起止日期。
- 成本租户时区与门店PMS时区不同则停止计算，要求核对日期归属；不会把午夜时间戳直接当作PMS营业日。

## 不生成误导数据

| 情况 | 处理 |
| --- | --- |
| 未配置、门店未唯一匹配、文件失败 | 保留成本账和中文原因，不生成每间次成本 |
| 只有出租率、物理总房数或口径未核验的soldRooms | 不反推间次，不拿其他字段兜底 |
| 只有旧版过夜房晚或钟点折合房晚 | 不直接改名当作间次，不与新口径混算 |
| 已核对总间次，四项明细全部或部分缺失 | 正常使用总间次，隐藏不完整分项，不将缺失当0 |
| 提供的分项为负数、小数、错误类型、部分和大于总数，或完整分项和不等于总数 | 停止计算，要求核对已提供的矛盾数据，不静默修正 |
| 缺天、重复、期望天数错误、交叉核验失败 | 不用不完整分母去摊完整成本 |
| 最新版本不合格 | 显示待核验，不静默退回更旧版本 |
| 同期部分逐日数据与旧月合计同时存在 | 以逐日完整性为门槛，不用旧月合计掩盖缺天 |
| 全部包含声明、按次计数、时区/日切未确认，或有分项却缺互斥说明 | 数量可作为待核验候选显示，但不作分母；无分项不要求互斥说明 |
| PMS明确确认零间次 | 展示0间次，比值为空而不是0元或无穷大 |
| 某类没有成本记录 | 显示无入账记录，不认定实际成本为0 |
| 耗用待审核 | 暂停耗品及清洁用品比值；洗涤独立以实际合格回收费用计算 |
| 原始零金额、历史分类待核对 | 暂停该类比值，需要业务核对；本期未新增历史成本重分类/零价确认工作流 |
| 两期PMS口径不同或基期成本不大于0 | 展示不可比及理由，不给百分比 |
| 发生净负成本 | 如分母有效则显示负数并保留冲销提示，不生成涨跌百分比 |

“可计算”只表示**已入账事实与PMS分母符合本计算口径**，不证明员工已经把所有业务录入，更不自动进入工资或正式KPI考核。

## 数据源接线（部署时显式启用）

1. `STORE_COST_PMS_TENANT_ID`：中台真实租户UUID，默认空即关闭。不能只凭OTA租户代码跨租户开放。
2. `STORE_COST_PMS_TENANT_CODE`：授权OTA/PMS来源租户代码，未设置时使用既有 `KPI_OTA_ALLOWED_TENANT_CODE`。
3. `STORE_COST_PMS_HOTEL_DIRECTORY_PATH`：已发布脱敏门店目录，未设置时使用 `KPI_OTA_HOTEL_DIRECTORY_PATH`。
4. `STORE_COST_PMS_SUMMARY_PATH`：已发布脱敏用房汇总，未设置时使用 `KPI_PMS_MONTHLY_SUMMARY_PATH`。旧文件可并存但不能改名复用旧房晚指标；建议成本专用发布文件。

目录沿用既有JSON数组格式：`tenantCode,hotelId,hotelCode,pmsProviderCode`。没有显式映射时，`hotelId` 必须同时唯一匹配中台 `hotel_profile.id`，`hotelCode` 必须唯一匹配 `property_code`，而不是组织UUID或门店名称。

两套系统独立建立门店档案时，ID可以不同。由接入方核对后，在**成本专用的服务端发布目录**中为该门店追加以下三个字段，不能通过浏览器请求传入：

| 字段 | 含义 |
| --- | --- |
| `coreTenantId` | 已授权中台租户UUID，必须与当前租户完全相同 |
| `coreHotelProfileId` | 已核对的中台 `hotel_profile.id`，不是组织UUID |
| `mappingEvidenceReference` | 真实映射核对凭据编号，非空文本，不包含账号密码或客人信息 |

`hotelId` 始终保留原PMS来源编号，汇总记录仍按原 `sourceHotelId` 读取；不得为接通新中台而批量改写历史来源编号或修改旧KPI目录。建议配置独立的 `STORE_COST_PMS_HOTEL_DIRECTORY_PATH`，让其他读取方保持原目录不变。

三个映射字段只要出现一个就进入显式映射模式，缺失、空白、类型错误、租户不符都拒绝匹配，不降级到“碰巧同ID”。中台档案、门店编码和来源编号在已授权来源租户内均须一对一；重复来源、一个中台档案连多个来源、旧格式与显式映射冲突均不计算。两套系统编码不同仍需接入侧另行核对，本轮不增加名称模糊匹配。每条汇总的 `sourceHotelCode` 也要一致；显式存在的 `tenantCode` 不一致时拒绝该源。

汇总沿用 `{"records":[...]}`；支持单日记录，或与请求起止日期完全相同的期间记录。要求：

- `sourceHotelId, sourceHotelCode, collectedAt, responseContentSha256`；采集时间不得早于期间结束或超出当前时间五分钟。
- `period.from,to,expectedDayCount,validDistinctDayCount,missingDates,duplicateDates`；天数与实际范围相等，缺失和重复数组必须存在且为空。
- `metrics.totalRoomUses` 必填，为包含全部类型的JSON非负整数值，允许0及数值上为整数的`2.0`，不接受字符串、负数、小数间次或单条超过十亿。逐日求和使用精确数值运算。
- 以下四个分项可全部省略：`paidOvernightRoomUses`收费过夜、`complimentaryRoomUses`免费（含免费钟点）、`houseUseRoomUses`自用（含自用钟点）、`paidHourlyRoomUses`收费钟点。提供时须为非负整数；null视为未提供，不视为0。
- 部分分项合计不能超过总间次，四项完整时必须精确等于总间次。部分明细隐藏但总数可用；跨日聚合只在所有天均有完整明细时展示期间分项。总数不能由旧`overnightSoldRoomNights`或`totalUsedRoomNights`回退补齐，也不倒推未知分项。
- `validation.coverageState,numericState,aggregateCrosscheckState` 都是 `PASS`。
- `roomUseDefinition` 为成本分母的额外验收约定，不能因为出租率曾经通过KPI验收就自动设置它。总数模式的最小口径定义：

```json
{
  "code": "ALL_ROOM_USES_V1",
  "verificationState": "CONFIRMED",
  "hourlyRooms": "INCLUDED",
  "complimentaryRooms": "INCLUDED",
  "houseUseRooms": "INCLUDED",
  "unit": "ROOM_USE",
  "countingRule": "EACH_USE",
  "timezone": "Asia/Shanghai",
  "businessDayCutoff": "04:00",
  "evidenceReference": "由接入方填写真实口径验收凭据编号，不可用本示例冒充"
}
```

上面仅为格式示例，**业务规则确认不等于真实PMS字段已经验收**。三类包含声明均须为 `INCLUDED`。接入方核对总数的字段定义和同房多次计数后才填写 `CONFIRMED`；不能改旧记录标记冒充新口径。字段说明或脱敏总数样本即可作为核对材料，无需完整日报、客人明细或钟点折算。提供任何可选分项时另需`breakdownRule=FREE_AND_HOUSE_USE_FIRST`，未提供分项时无需此字段。

来源供应商、口径代码、单位、按次规则、时区或日切不一致时不能混算。可选分项的有无不改变总间次可比性。接口固定返回 `roomUseBasis=ALL_ROOM_USES_V1`，数量为`roomUses/candidateRoomUses`，单价为`perRoomUse`；前端拒绝缺少新标识或旧标识响应，防止把房晚误显示为间次。

仅供测试说明：全部用房2间次、某类成本20元，结果为10元/间次，无需四类分项。另一例过夜200、免费10、自用5、钟点5，合计220间次、成本88元，结果为0.4000元/间次。均非真实门店数据。

部署前应由现有数据接入侧发布这层规范汇总，原文件未提供该扩展时只显示“待核验”。不改写既有KPI读数与计算逻辑、不共享外部浏览器Cookie、不直接连其他业务数据库。

目录上限1MiB、汇总64MiB/10万条。汇总流式读取，只保留匹配门店的数据；单次分析共用同一来源快照计算本期、环比和同比，避免三次读取混用不同版本。发布方应使用原子替换，不能边写半个JSON边对外提供。重复键、重复同时间版本及损坏文件均关闭计算，不返回原始载荷、密码、路径或客人明细。

## 月结、来源修订与三年保留

- 原V66成本月结不可覆盖，本功能不新增写接口或数据库迁移。
- 本页PMS指标使用最新已发布数据，**不是已经冻结的PMS/KPI结算快照**。PMS修订可以使相同已关账成本的最新比值变化；页面记录采集时间和本次来源指纹，同时告知成本月结未改变。
- 过往成本、工作汇总和KPI不跟随5天图片删除。要保证PMS/OTA三年同比追溯，接入侧必须保留至少36个月规范营业日数据及修订版本，并将发布包按版本备份。
- 本阶段的只读文件适配器不承担上游三年存档，不会从一份被覆盖的快照恢复历史，也没有自动归档或删除源文件的后台任务。上线前需验证既有接入任务的保留范围；正式KPI固化仍是独立确认流程，不能把实时分析当作固定历史绩效。
- 2026-09-19后续核查发现：云端月度发布数据陈旧、全部用房分项缺失，独立归档的日事实策略只有2年；本地已修复旧月度采集器的120条截断并增加版本留存，尚未部署，也未替代云端独立归档。当前证据、收口次序与材料要求见 [STORE-COST-PMS-LIVE-PREFLIGHT.md](STORE-COST-PMS-LIVE-PREFLIGHT.md)。
